# 会话错误复盘

## 分析会话

1. 只使用当前会话中可见的失败、重试、修正和用户反馈作为证据。
2. 合并症状不同但根因相同的问题；不要把推测或潜在风险当成已发生错误。
3. 仅当同一根因独立出现至少两次时，认定为反复错误；单次问题只列为观察项。
4. 尽可能用已成功的重试、日志或配置验证根因，不要仅凭报错文本归因。

## 判断归属

- 归为项目问题：根因来自仓库代码、配置、脚本、依赖、测试数据或项目约定，且预计随项目在其他机器复现。
- 归为本机环境问题：根因来自操作系统、Shell、编码、权限、路径、代理、已安装工具或 Agent 全局配置，且预计跨项目复现。
- 归为证据不足：无法可靠判断归属；只报告，不写入任何文件，也不要同时写入两个作用域。

项目规则目标为项目根目录的 `AGENTS.md`。本机规则目标为当前 Agent 类型根目录的 `AGENTS.md`；Codex 优先使用 `$CODEX_HOME/AGENTS.md`，未设置时使用 `~/.codex/AGENTS.md`。其他 Agent 的根目录不明确时，先向用户确认，不要猜测。

## 先提交候选报告

修改文件前，简洁列出：

- 问题及重复证据
- 根因与归属
- 经验总结
- 候选规则原文
- 目标文件及拟执行动作：新增、替换或无需修改

没有反复错误时明确说明，不为凑数创建规则。提交报告后停止，等待用户明确批准。

## 获批后写入

1. 只处理用户明确批准的规则和目标文件。
2. 写入前重新读取目标文件，确认其编码、现有规则和项目根目录。
3. 进行语义去重；已有规则足够时不修改，已有规则过于模糊时先提议替换。
4. 将每条规则压缩为一句可执行、可复用的指令；不要写事故经过、敏感信息或一次性绝对路径。
5. 使用最小补丁并保持原有结构、编码和换行风格，不修改无关内容。
6. 完成后报告实际修改的文件和规则；不要自行运行项目单元测试或构建。
